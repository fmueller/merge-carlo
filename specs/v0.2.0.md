# merge-carlo v0.2.0

## Summary

Draft, not active. This spec holds work the maintainer deferred from v0.1.0 so
that it no longer gates the first release. It defines no new simulator
behavior yet; scope beyond the areas below needs a spec change first.

## Goals

- Measure mutation efficacy for simulation dataclass methods that the v0.1.0
  mutation tooling cannot discover.
- Optionally enrich collected datasets with CI check and status observations.
- Explore quality-adjusted workflow simulation without turning defect or
  contributor estimates into individual performance scores.
- Support revising completed tracked work through a supported tooling path.

## Potential Features

### CI Enrichment

Collection can optionally enrich a dataset with check-run and commit-status
metadata for known, correctly attributed commit SHAs, preserving attempt and
completeness information. Missing checks are unknown, never successful; checks
on different SHAs, merge-test SHAs, or reruns are never merged into one timeless
result; and a legacy status without a start event yields no runtime. An
unavailable CI endpoint records `unavailable`, still produces a complete core
dataset, and disables CI-derived estimates. v0.1.0 ships without this
enrichment.

### Tracked-Work Tooling

Completed tracked work can be reopened when the maintainer revises its accepted
outcome, through a supported, pinned Taskrail command path that neither
hand-edits machine-managed fields nor erases prior verification history.
merge-carlo does not reimplement Taskrail internals. This is repository tooling,
not simulator behavior.

### Mutation Discovery

Mutation testing covers methods of decorated simulation classes, including
calendar materialization and pull-request lifecycle transitions, once the
pinned mutation tool can discover them. v0.1.0 pins mutmut 3.7.0, which skips
every decorated class body; the fix (boxed/mutmut#539) is merged upstream but
unreleased. The remedy is a released, bounded mutmut version, not a git pin, a
patched tool, or production code restructured for the tool. Methods the tool
still cannot discover, such as `@property` methods, carry an explicit
limitation, and per-module reports never imply coverage of undiscovered code.
The v0.1.0 per-module floor, ten-mutant minimum, and differential scope rules
continue to apply.

### Quality-Adjusted Workflow Simulation

The simulator may later model software quality as a separate, optional layer
over the review workflow. The first step is a versioned quality-outcome
contract that defines an introduced defect, detection by tests or review,
post-merge escape, severity, detection delay, and remediation work. Historical
linkage must be explicit and conservative; a requested change, a failed check,
or a closed pull request is not itself a defect.

Quality evidence must retain separate tiers: pre-merge CI or test failure,
static-analysis finding, confirmed functional defect, production incident or
regression, revert, and remediation change. A static finding is a quality-risk
proxy, and a revert is an operational signal; neither is silently promoted to
an escaped-defect label. Benchmark test passage is also not production-quality
evidence. Every tier records its observation window, denominator, linkage basis,
and censoring or missingness treatment.

Defect incidence uses changed-code size as an exposure measure, not as a
standalone causal rule. Candidate predictors include added and deleted lines,
file or module churn, complexity or dependency fan-out where available,
historical defects, tests and CI evidence, ownership familiarity, review depth,
and task type. Sparse and overdispersed defect counts require uncertainty-aware
calibration and held-out descriptive validation. Source-code metrics are
optional future inputs and do not expand the v0.1.0 ingestion boundary.

AI-origin effects are modeled as declared, uncertain cohort assumptions or
interactions, never as a universal multiplier or an inferred percentage of
AI-written code. Human, AI, non-AI automation, and unknown origin remain
separate concepts, and unknown remains a valid result. Scenario comparisons
must show assumption sensitivity rather than present an AI effect as causal.

Agentic work records process dimensions separately from origin where evidence
exists: assisted versus agent-authored work, tool or agent family and version,
autonomy level, human intervention and revision effort, agent iterations, test
and tool-use behavior, reviewer engagement or abandonment, and repository
context or instructions. These observations must not be collapsed into a
single agent-quality score or treated as intrinsic contributor traits.

Merge behavior is modeled as a conditional merge or closure hazard based on PR
attributes such as task type, changed size and files, CI outcomes, review state,
review engagement, revisions, abandonment, policy, capacity, and queue
conditions, not as an intrinsic probability attached to an individual
contributor. If contributor or agent effects are eventually needed, they use
pseudonymous, pooled or hierarchical effects with shrinkage and minimum-sample
safeguards; default reports remain repository- and cohort-level and do not rank
people.

Validation must use temporal holdouts where possible, matched human baselines
where available, repository-level or hierarchical effects, and explicit
selection correction for merged-only or survivor-conditioned data. Agent,
repository, task, and language imbalance must be reported rather than hidden by
pooled rates. Observational associations must not be presented as intervention
effects.

An implemented quality layer may generate remediation work after escaped
defects, allowing defect detection and rework to consume review capacity and
alter later queue and merge outcomes. Reports may expose escaped-defect rates,
time to detection, remediation demand, and quality-adjusted throughput only
with their denominators, provenance, uncertainty, and censoring rules. The
feature must not claim productivity gains, safe approval policies, or
individual developer quality without intervention evidence; those claims remain
out of scope.

The first v0.2.0 quality slice is the data contract and descriptive reporting
of these signals, including optional CI and static-analysis observations. A
latent defect-introduction model, post-merge detection, remediation feedback,
and contributor or agent effects are subsequent milestones and require evidence
that passes the validation safeguards above. Source-code metrics remain
optional future inputs and do not silently expand the v0.1.0 ingestion boundary.

### End-to-End Holdout Validation Preparation

The real-data workflow can prepare a chronological training/validation split
from a collected dataset, calibrate only on the training interval, and emit the
versioned replay-evidence input consumed by `merge-carlo validate`. The holdout
replay uses only known-at-arrival attributes, requires adequate follow-up for
mature cohorts, and preserves dataset, model, and replay content hashes. A
held-out run remains distinguishable from an `in_sample_diagnostic`, even when a
declared descriptive gate fails. The workflow does not tune parameters on the
holdout or establish intervention validity.

## Caution

Mutation scores computed with the v0.1.0 tooling must not be reinterpreted as
covering dataclass methods after the tool changes; compare raw discovery before
and after.

## Recommendation About LLM Support

Unchanged from v0.1.0: no LLM calls.

## Explicitly Excluded

Everything not listed under Potential Features, until this draft is extended
through a spec change.
