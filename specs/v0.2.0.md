# merge-carlo v0.2.0

## Summary

Draft, not active. This spec holds work the maintainer deferred from v0.1.0 so
that it no longer gates the first release. It defines no new simulator
behavior yet; scope beyond the areas below needs a spec change first.

## Goals

- Measure mutation efficacy for simulation dataclass methods that the v0.1.0
  mutation tooling cannot discover.
- Optionally enrich collected datasets with CI check and status observations.
- Support revising completed tracked work through a supported tooling path.

## Potential Features

### CI Enrichment

Collection can optionally enrich a dataset with check-run and commit-status
metadata for known, correctly attributed commit SHAs, preserving attempt and
completeness information. Missing checks are unknown, never successful; checks
on different SHAs, merge-test SHAs, or reruns are never merged into one timeless
result; and a legacy status without a start event yields no runtime. An
unavailable CI endpoint records `unavailable`, still produces a complete core
dataset, and disables CI-derived estimates. v0.1.0 ships without this
enrichment.

### Tracked-Work Tooling

Completed tracked work can be reopened when the maintainer revises its accepted
outcome, through a supported, pinned Taskrail command path that neither
hand-edits machine-managed fields nor erases prior verification history.
merge-carlo does not reimplement Taskrail internals. This is repository tooling,
not simulator behavior.

### Mutation Discovery

Mutation testing covers methods of decorated simulation classes, including
calendar materialization and pull-request lifecycle transitions, once the
pinned mutation tool can discover them. v0.1.0 pins mutmut 3.7.0, which skips
every decorated class body; the fix (boxed/mutmut#539) is merged upstream but
unreleased. The remedy is a released, bounded mutmut version, not a git pin, a
patched tool, or production code restructured for the tool. Methods the tool
still cannot discover, such as `@property` methods, carry an explicit
limitation, and per-module reports never imply coverage of undiscovered code.
The v0.1.0 per-module floor, ten-mutant minimum, and differential scope rules
continue to apply.

## Caution

Mutation scores computed with the v0.1.0 tooling must not be reinterpreted as
covering dataclass methods after the tool changes; compare raw discovery before
and after.

## Recommendation About LLM Support

Unchanged from v0.1.0: no LLM calls.

## Explicitly Excluded

Everything not listed under Potential Features, until this draft is extended
through a spec change.
