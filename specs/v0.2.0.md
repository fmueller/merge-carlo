# merge-carlo v0.2.0

## Summary

Draft, not active. This spec holds work the maintainer deferred from v0.1.0 so
that it no longer gates the first release, and it adds two new simulator
behaviors: an optional merge queue between approval and merge, and a core
trunk-based integration model that compares direct-to-trunk integration with
short-lived and longer-lived pull-request branches through to production
deployment, including pipeline speed and reliability. v0.3.0 builds feature
activation, further review policies, follow-up work, and workflow profiles on
top of this core, and v0.4.0 adds shared CI and deployment capacity, trunk
breakage, and rollback. Scope beyond the areas below needs a spec change
first.

## Goals

- Measure mutation efficacy for simulation dataclass methods that the v0.1.0
  mutation tooling cannot discover.
- Optionally enrich collected datasets with CI check and status observations.
- Model a merge queue as an optional, typed gate on the existing pull-request
  lifecycle, so queue wait, batching, ejection, and rebuild cost become visible
  instead of being folded into an opaque approval-to-merge delay.
- Compare direct-to-trunk, short-lived pull-request, and longer-lived
  pull-request integration over the same latent work, with blocking or
  continuous post-integration review, and with or without a merge queue.
- Model the delivery pipeline from integration to production with declared
  speed and reliability, so deployment wait, failures, and fix-forward delay
  are visible for every integration policy.
- Explore quality-adjusted workflow simulation without turning defect or
  contributor estimates into individual performance scores.
- Support revising completed tracked work through a supported tooling path.
- Expose model calibration as an offline `merge-carlo calibrate` CLI command so
  a collected repository dataset can be calibrated without writing Python.

## Potential Features

### CI Enrichment

Collection can optionally enrich a dataset with check-run and commit-status
metadata for known, correctly attributed commit SHAs, preserving attempt and
completeness information. Missing checks are unknown, never successful; checks
on different SHAs, merge-test SHAs, or reruns are never merged into one timeless
result; and a legacy status without a start event yields no runtime. An
unavailable CI endpoint records `unavailable`, still produces a complete core
dataset, and disables CI-derived estimates. v0.1.0 ships without this
enrichment.

### Calibration Command

`merge-carlo calibrate` runs the existing v0.1.0 calibration path from the
command line: it exports one extraction from a projected dataset produced by
`collect`, builds frozen-cutoff features, merges the explicitly supplied
active-review-effort assumptions, and writes `model.json`, `calibration.json`,
and `model-card.md` into an empty or absent output directory, or replaces an
existing bundle only with an explicit `--overwrite`. The written `model.json` is
accepted by `simulate` unchanged. The command is a thin layer over
`build_features`, `calibrate_model`, and `write_calibration`; for the same
inputs it produces byte-identical artifacts to the Python API, and it changes no
calibration semantics, defaults, or evidence safeguards.

Every input is named explicitly: the dataset path, the private workspace-key
path needed to export it, the calibration-coverage record, the assumptions file,
the declared human-reviewer identifiers, a timezone-aware training cutoff, the
model timezone, and the fixed outcome horizon. When a dataset holds more than
one extraction, the caller selects one; the command never picks one silently.
It does not derive coverage, guess human reviewers, infer work origin, or fill
in a missing active-effort assumption, and it never derives active effort from
an observed elapsed review delay. No optimizer tunes parameters to reproduce
historical latency.

The command is offline: it needs no `GITHUB_TOKEN` and makes no network
request. The workspace key, tokens, bodies, patches, and email addresses never
appear in its output artifacts, console messages, or errors. A coverage record
whose dataset content hash does not match the exported extraction, an unknown
or ambiguous extraction, missing cohort assumptions, a naive cutoff, an unknown
timezone, or a non-positive horizon fails with exit code `2` and a specific
message, writing no partial bundle. An unreadable dataset or key fails with exit
code `3`. A successful run labeled `exploratory_only` or
`synthetic_demonstration` still exits `0` and reports its evidence flags; the
`--json` console mode emits them as structured messages.

`calibrate` does not split a dataset or validate a model. Chronological holdout
preparation, below, may reuse it for the fitting interval, but an in-sample
calibration is never labeled held out. The Python calibration API remains
supported.

### Merge Queue

The simulator can place a merge queue between approval and merge. A pull
request whose current revision satisfies its verification gate and either a
completed human review or an explicitly enabled bypass enters the queue instead
of merging at once. Without a declared queue policy, v0.1.0 semantics are
unchanged. The queue is a closed, typed policy with provenance on every
parameter. It does not load code dynamically, and it is not an emulation of
GitHub or any other hosting product. Trunk-Based Integration below reuses this
contract as an integration gate, so it must not assume that every queue entry
is a pull request.

Queue mechanics. Entries are ordered by `(enqueued_at, pr_id, revision)`. The
policy declares a maximum merge-group size, a minimum group size with a bounded
wait after which a smaller group starts anyway, and a maximum number of groups
that may build at the same time. Groups form from consecutive entries. Each
group builds speculatively on trunk plus every earlier group still building.
Group verification is aggregate elapsed time drawn from a declared
distribution, with no runner-capacity queue, matching v0.1.0 verification. A
group merges only after it passes and every earlier group has merged, and its
members merge at that time in queue order.

Failure and ejection. Each entry carries a latent queue-failure draw keyed by
replication, pull request, revision, queue attempt, and event purpose, never by
group composition or scenario identifier. Paired scenarios with different group
sizes or concurrency therefore share the same failing changes. A group fails
when any member's draw fails, or when a declared per-build flake draw fires.
Locating the failing member uses one of two closed rules:

- `oracle_isolation` identifies the failing member immediately. It is an
  optimistic bound and is labeled as one wherever it is reported.
- `bisect` splits the failed group into halves, with the first half taking the
  larger share, and rebuilds them until the failing member is isolated. Each
  rebuild consumes elapsed time and counts as a build.

An ejected member leaves the queue. Every later group whose speculative base
included it is invalidated and rebuilds without it. Ejection reasons are
`member_failure`, `merge_conflict`, `retry_exhausted`, `abandoned`, and
`superseded`:

- A member failure or a declared merge-conflict draw returns the pull request
  to AUTHOR_RESPONSE. The resulting new revision invalidates prior approval and
  verification under the v0.1.0 rules.
- A flaky build retries up to a bounded attempt count. When the count is
  exhausted, the group's members re-enter the queue tail without a new revision.
- A new revision pushed while an entry is queued removes the entry.
- An abandonment deadline still competes with merge. Abandonment removes the
  entry, and a deadline at or before a candidate merge wins.

The v0.1.0 engine safety limit applies to queue attempts and builds. At the
horizon, a queued or building entry is censored, never merged or rejected.

The first slice excludes priority jumps, entries that must build alone,
per-check subsets of required checks, multiple target branches, build-runner
capacity, and trunk breakage. Because a no-queue baseline does not model trunk
breakage either, the queue's main benefit is not represented in v0.2.0;
v0.4.0 adds it. Every
comparison between queue and no-queue scenarios must state this visibly, and a
report may not present the queue's added latency or build cost as a net loss.

Scenarios. The closed scenario enumeration gains:

- a no-queue baseline;
- a queue with group size one;
- batched group sizes;
- changes to build concurrency;
- `oracle_isolation` compared with `bisect`; and
- queue scenarios combined with the existing demand, calendar, absence, and
  bypass overrides.

Each override changes only queue policy, so the latent work and failure draws
stay shared across scenarios.

Metrics. Reports add the following, each with its denominator, eligibility,
censoring, and undefined reason:

- enqueue-to-merge latency and wait from enqueue to group start;
- builds and verification attempts per merged pull request, and rebuilds caused
  by earlier ejections;
- the distribution of merge-group sizes;
- ejections by reason;
- peak and time-average queue length;
- utilization of the declared build concurrency; and
- queue entries censored at the horizon.

Ready-to-merge latency remains end to end. Build-concurrency utilization is not
runner utilization.

Data and calibration. Where the source exposes queue history, collection may
record queue entry and removal events. On GitHub these are the
`AddedToMergeQueueEvent` and `RemovedFromMergeQueueEvent` pull-request timeline
items, which carry a removal reason. If the REST API cannot supply them, the
adapter may issue read-only GraphQL queries under the same rules as REST:

- no mutation;
- no enqueue or dequeue operation;
- the approved API origin only;
- token redaction; and
- bounded sizes and collection status.

A queue configuration read from the source is a current snapshot with its
retrieval time. It is never assumed to apply to earlier history. Group
verification durations come from CI-enrichment observations on merge-group
commits, which are kept separate from checks on the pull-request head.
Observed enqueue-to-merge delay includes queue wait and must never be sampled
as group verification time. A repository without collected queue history
records queue status `unavailable`, not "no queue". A removal reason maps to an
ejection reason only when the source states it, and otherwise it is `unknown`.
Held-out replay may compare enqueue-to-merge latency and ejection rates
descriptively under the existing validation rules. It does not establish that
a queue improves stability or quality.

Acceptance rests on hand-calculated fixtures. In each fixture, three pull
requests enter the queue at time zero, no minimum-size wait applies, and group
verification takes a constant 600 seconds:

- With group size one and concurrency one, they merge at 600, 1,200, and 1,800.
- With group size three, all three merge at 600.
- With group size one and concurrency three, all three merge at 600.
- In that last configuration, if the middle entry fails under
  `oracle_isolation`, the first merges at 600 and the middle is ejected at
  600. The third rebuilds from 600 and merges at 1,200.

A further hand-calculated fixture must cover `bisect`. Property tests must show
the following:

- pull requests are conserved through the queue;
- a merge always comes from a passed group that contains the member's current
  revision;
- no group merges before an earlier group;
- an ejected attempt never merges; and
- latent failure draws are identical across group-size scenarios.

### Trunk-Based Integration

This feature answers one systems question:

> Under declared work-packaging, verification, integration-friction, review,
> and delivery-pipeline assumptions, how do direct-to-trunk and
> short-lived-branch workflows compare with longer-lived pull-request branches,
> from ready work to production deployment?

Results are conditional simulated outcomes, not causal evidence, productivity
measurement, or a safety certification. The pull-request lifecycle from v0.1.0
remains available unchanged. This feature adds a separate typed workflow model
and must not silently change v0.1.0 semantics.

#### Model boundary

The model begins with latent work increments that are ready to enter the
modeled integration workflow. Coding time, task selection, developer WIP, and
the process that produced those increments stay outside the boundary. Branch
lifetime, packaging cadence, and batch size are declared scenario inputs, not
consequences of simulated coding behavior.

Integration is the point at which an integration batch reaches trunk in the
abstraction. The model performs no Git write. Production deployment is a
separate, later event produced by the delivery pipeline below, and in v0.2.0 it
is the last modeled delivery event. Reports must not call integration
"deployment" or "release", and must not call deployment user-visible. Feature
activation and features as units of user-visible work are v0.3.0 scope. Human
review is a separate activity that may happen before or after integration.

The model does not ingest source code, judge design quality, detect defects,
estimate AI-written code, infer productivity, or predict security outcomes.
"Review finding" and "requested change" are workflow observations or
assumptions, not defect labels.

#### Work and integration units

The domain must distinguish:

- a latent work increment, the smallest conserved unit shared by paired
  scenarios;
- an integration batch, which packages one or more increments for one attempt
  to reach trunk; and
- the commits or pull request representing that batch, where the input evidence
  can establish them.

Paired scenario comparisons begin with the same latent increments. Integration
policies may group those increments differently, but they must conserve
increment identity and count. A scenario may not gain an apparent flow advantage
by dropping, duplicating, or regenerating underlying work.

#### Integration policies

The typed integration-policy contract supports at least:

- `direct_to_trunk`, in which each eligible batch integrates without a
  pull-request branch after it satisfies its declared gates;
- `short_lived_pull_request`, in which small batches use a bounded-lifetime
  branch and pull request; and
- `long_lived_pull_request`, the comparison policy, in which larger or older
  batches integrate through a pull request.

Batch-size and branch-lifetime distributions, maximums, and packaging cadence
are explicit, versioned scenario inputs with provenance. "Short-lived" and
"long-lived" are not hard-coded universal durations. Presets may provide
documented defaults, but reports must render their resolved values.

Packaging rules are closed and typed, not dynamically loaded code. The first
slice supports one increment per batch, and a bounded rule that closes a batch
at a configured increment count, elapsed age, or cadence boundary, whichever
applies first. Increment selection is stable by `(ready_at, increment_id)`, and
a rule may not inspect future arrivals. Historical replay may preserve an
observed grouping when its membership is explicit and complete.

Integration policy, integration gate, and human-review policy are separate
dimensions. Named presets may bundle realistic combinations, but the scenario
contract must also allow factorial comparisons where a combination is
semantically valid. Invalid combinations are rejected, never silently
rewritten.

#### Integration gates

The integration gate decides how a verified batch reaches trunk. Two closed
gates are supported:

- `direct_verification`: the batch is verified against its own base and then
  integrates.
- `merge_queue`: the batch enters the Merge Queue contract above, which handles
  ordering, grouping, speculative builds, build concurrency, failure isolation,
  ejection, rebuilds, and censoring.

Both gates are valid with all three integration policies. Here a queue entry is
an integration batch. Under `direct_to_trunk`, the batch enters a
pre-integration queue without a pull request. Entries are ordered by
`(enqueued_at, batch_id, attempt)`.

Latent failure draws are keyed by each conserved increment and its attempt,
never by batch composition or scenario identifier. A batch fails when any of
its increments fails. Paired scenarios that package the same increments
differently therefore share the same failing work. Under `merge_queue`, queue
group verification is the batch's automated verification gate. The
verification-failure and retry assumptions below feed the queue's failure and
flake draws instead of adding a second gate. An ejected batch returns to its
integration policy for rework. It is never integrated in the failed attempt,
and its increments stay conserved.

Trunk breakage is excluded. Under `direct_verification`, a batch verified
against a stale base can break trunk in practice. The model does not represent
that breakage, so it does not represent the risk a merge queue exists to
remove. Every comparison across integration gates must state this visibly. The
queue's added latency or build cost must not be presented as a net loss, and
the absence of a queue must not be presented as safe.

#### Verification and integration friction

Every integration batch must satisfy its declared automated verification gate.
The model supports bounded verification failures and retries, plus conflict or
rebase delay. These are workflow events, not evidence of a defect or a measure
of developer productivity.

Scenarios may declare provenance-tagged friction distributions directly. They
may instead declare bounded response curves that relate friction to inputs such
as branch age, batch size, or intervening trunk integrations. The product does
not build in a universal monotonic relationship. A fitted historical response
curve is preferred when its evidence is sufficiently complete, validated on a
temporal holdout, and used within its observed support. Otherwise the model
falls back to explicit assumptions and sensitivity analysis. Extrapolated
counterfactuals must be labeled as such.

Observed elapsed branch, CI, or pull-request duration must not be treated as
active conflict-resolution or verification effort. Missing conflict events,
rebases, retry causes, or direct-to-trunk history remain unavailable rather than
being reconstructed from commit messages or weak merge-state heuristics.

#### Review policies

The typed human-review contract supports:

- `blocking_review`: verification, human review, then integration; and
- `continuous_post_integration_review`: verification, integration, then a
  required human review item that enters a continuous queue.

The existing hypothetical review bypass remains a separate policy. It means
that no human review is scheduled for eligible work, and it must not be
presented as continuous post-integration review. Non-blocking review must never
be described as evidence that integrated code is safe or defect-free. Batched,
paired, and mixed audited/non-audited review policies are v0.3.0 scope.

Post-integration review items consume the same active-review capacity
accounting as other reviews: duty calendars, absences, no self-review, stable
ordering, interruption handling, and the separation of active and off-duty
time. Queue ordering, simultaneous-event precedence, horizon censoring, and
review service assumptions are deterministic and documented. A review item
unfinished at the horizon is review debt. It is neither a successful review nor
a failed integration.

#### Delivery pipeline

After integration, work reaches production through a modeled deployment
pipeline. The pipeline is a typed policy with provenance on every parameter. Its
speed and reliability are declared assumptions or calibrated observations,
never constants built into the product.

Triggers. The pipeline deploys trunk in integration order. A closed trigger
policy decides when a deployment run starts:

- `per_integration`: a run starts when a batch integrates and no run is in
  progress; and
- `scheduled`: runs start at declared calendar times or on a declared cadence.

At most one run is in progress at a time. A run deploys every integrated batch
that is not yet deployed when the run starts. Batches that integrate during a
run wait for the next run. This one-run rule is pipeline ordering, not a
runner-capacity model.

Speed. A run takes aggregate elapsed time drawn from a declared distribution,
with no runner-capacity queue, matching v0.1.0 verification. Observed pipeline
duration is elapsed time and must never be treated as active effort.

Reliability. A run fails when any increment it carries fails its latent
deployment-failure draw, or when a declared per-run flake draw fires. The draws
are keyed by replication, increment, deployment attempt, and event purpose,
never by run composition or scenario identifier, so paired scenarios share the
same failing work. Failure handling is closed:

- `flake`: the run retries up to a bounded attempt count;
- `increment_failure`: the pipeline waits a declared fix-forward delay; and
- `retry_exhausted`: a flake that exhausts its retries waits the same
  fix-forward delay.

A failed run deploys nothing, and production keeps the previously deployed
state. Because the pipeline deploys trunk in order, a failed run blocks every
later deployment until its fix-forward delay ends. The next run then includes
all waiting batches, and the failing increment draws again with its next
attempt. The fix-forward delay is elapsed time. It consumes no review capacity
and is not modeled coding effort, and reports say so. A deployment failure is a
workflow event, not evidence of a defect, and it never revives or undoes an
integration. The v0.1.0 engine safety limit applies to deployment attempts.

At the horizon, integrated work that is not yet deployed is censored, never
counted as deployed or as failed. Deployment is not user-visible activation:
reports may say work reached production, never that users received it.
Feature activation is v0.3.0 scope.

#### Integration, deployment, and review state

The domain uses separate lifecycle records, or an equivalent typed design:

- an integration batch reaches a terminal integrated, closed, or censored state;
- a deployment run records its trigger, start, attempts, the batches it
  carries, its outcome and failure reason, and censoring, and each integrated
  increment records whether it was deployed or censored;
- a post-integration review item records queue entry, review start, completion,
  reviewer, and censoring;
- a completed review may record requested changes or other declared findings;
  and
- every record has explicit provenance for observed, derived, proxy, assumed, or
  synthetic values.

A finding is counted but creates no follow-up work in v0.2.0. Follow-up work is
v0.3.0 scope. Until then, reports must state that remediation after a
post-integration finding is not modeled. Terminal-state invariants must prevent
a post-integration finding, abandonment deadline, or horizon event from reviving
or undoing an integrated batch.

#### Metrics

Reports distinguish at least:

- ready-to-integration, ready-to-deployment, and integration-to-deployment
  latency;
- deployment runs, attempts per deployed increment, failed runs by reason, and
  the run failure rate with its denominator;
- time the pipeline spends blocked on fix-forward, and increments deployed per
  run;
- integrated work not yet deployed at the horizon;
- integration-to-review-start and integration-to-review-completion latency;
- integration-batch size and age, branch lifetime, verification attempts and
  retries, and declared conflict or rebase delay;
- under `merge_queue`, the queue metrics per integration policy;
- review queue peak, time-average length, and review-debt count at the horizon;
- review-debt age or bounded age quantiles;
- reviewer active utilization and declared capacity;
- integrated work still awaiting review; and
- completed reviews with requested changes or findings.

All metrics need explicit denominators, eligibility, censoring, and undefined
reasons. A report must never replace missing review capacity with zero review
latency, or treat accumulating review debt as a favorable integration result.

The report presents integration speed, deployment speed, deployment failure
and fix-forward cost, review debt, verification rework, queue build cost, and
conflict cost as a trade-off vector. No single metric is the
default winner or an optimization objective. Paired comparisons reuse shared
demand and latent draws where the work item is common. Any apparent
improvement is labeled conditional on the workflow, capacity, and gate
assumptions.

The report may say that a scenario produces faster modeled integration under
its assumptions. It may not declare trunk-based development or any other
scenario universally superior, safe, or causally effective. Reversals across
assumption sets are reported with a measurement recommendation, not a policy
ranking. A visible limitations section states that the model does not
establish defect escape, security risk, policy safety, business value, or
individual performance.

#### Data and calibration

The input contract supports explicit branch, commit, pull-request, merge-queue
entry and removal, integration, deployment, and post-integration review events,
including event ordering where available. Direct-mainline commits, conflict
work, and review-tool metadata each carry collection completeness. They are
represented as unavailable or partial when the source cannot establish them,
and they are never reconstructed from unreliable text heuristics.

Active review effort remains assumed or explicitly supplied. Observed elapsed
integration or feedback delay must not be sampled as active service and then
have a simulated queue added on top. Historical replay may validate descriptive
timing and volume distributions. Replay or fitting must not claim that trunk
integration or non-blocking review caused better quality, faster delivery, or
higher productivity. Insufficient evidence remains an explicit outcome.

Pipeline speed and reliability may be calibrated from two read-only sources.
CI Enrichment check runs on trunk commits supply pipeline durations and
outcomes, kept separate from pull-request head and merge-group checks. GitHub
deployments and deployment statuses, read through the existing REST adapter
with no write method, supply deployment timing and outcomes. The operator
declares which environments count as production; an environment name is never
interpreted on its own. A repository without collected deployment history
records deployment status `unavailable`, not "no pipeline" and not instant
deployment. A failed or errored deployment status is a pipeline observation,
not a defect label. Observed redeployments and rollbacks are kept as
observations but are not modeled until v0.4.0, and a repository that relies on
them is marked `partial`.

#### Scenarios and verification

The scenario suite exercises at least:

1. a longer-lived pull-request and blocking-review baseline;
2. short-lived pull requests over the same latent increments, with blocking
   review;
3. verified direct-to-trunk integration with continuous post-integration
   review;
4. direct-to-trunk integration with and without a pre-integration merge queue,
   compared with short-lived pull requests through a queue;
5. reviewer absence and additional demand across integration policies;
6. `per_integration` compared with `scheduled` deployment over the same
   integrations; and
7. pipeline duration and failure rate varied across integration policies that
   share the same latent increments.

Synthetic fixtures include:

- common latent increments grouped into different batches;
- a verification retry and a bounded conflict delay;
- no available reviewer, and review capacity that drains accumulated debt;
- a finding after integration;
- a batch ejected from a speculative queue group, which forces later groups to
  rebuild; and
- the same failing increment packaged into different batches under two
  policies;
- a flaky deployment run that succeeds on retry; and
- a failed deployment that blocks later batches until fix-forward ends.

Deployment acceptance rests on hand-calculated fixtures with a
`per_integration` trigger, a constant 600-second run, and no flake draws:

- Two batches integrate at 0 and 300 seconds. The first run deploys the first
  batch at 600. The second batch waits for that run, and the second run deploys
  it at 1,200.
- In the same fixture, the first batch fails its deployment draw in the first
  run, and the fix-forward delay is 900 seconds. The first run fails at 600 and
  deploys nothing. The next run starts at 1,500 and deploys both batches at
  2,100.

Besides the repository's normal lint, type, test, and mutation checks, the
implementation must prove the following:

- latent increments are conserved across paired integration policies;
- the three integration policies resolve as distinct policies without changing
  shared work;
- integration policy, gate, and review policy vary independently, and invalid
  combinations are rejected;
- under `merge_queue`, an ejected batch is never integrated in that attempt and
  failure draws for a shared increment are identical across packaging policies;
- an integration can complete while its post-integration review waits;
- a post-integration review cannot alter a terminal integration state;
- no increment deploys before it integrates, a failed run deploys nothing, and
  a deployment failure never alters a terminal integration state;
- integrated increments are conserved as deployed or censored, and deployment
  failure draws for a shared increment are identical across packaging
  policies;
- review-debt accounting conserves created, completed, and unresolved items;
- blocking and continuous scenarios share equivalent latent demand inputs;
- unsupported historical fitting and extrapolation are rejected or visibly
  qualified;
- horizon censoring does not turn unfinished reviews or undeployed work into
  successes;
- every cross-gate comparison renders the trunk-breakage limitation; and
- reports render from saved artifacts without rerunning a simulation.

Excluded from v0.2.0:

- feature activation and features as units of work;
- CI and deployment runner capacity, rollback, staged rollouts, and multiple
  deployment environments;
- batched, paired, and mixed audited/non-audited review;
- follow-up work;
- professional workflow profiles;
- trunk-breakage propagation; and
- any simulation of coding time, task selection, or developer WIP.

### Tracked-Work Tooling

Completed tracked work can be reopened when the maintainer revises its accepted
outcome, through a supported, pinned Taskrail command path that neither
hand-edits machine-managed fields nor erases prior verification history.
merge-carlo does not reimplement Taskrail internals. This is repository tooling,
not simulator behavior.

### Mutation Discovery

Mutation testing covers methods of decorated simulation classes, including
calendar materialization and pull-request lifecycle transitions, once the
pinned mutation tool can discover them. v0.1.0 pins mutmut 3.7.0, which skips
every decorated class body; the fix (boxed/mutmut#539) is merged upstream but
unreleased. The remedy is a released, bounded mutmut version, not a git pin, a
patched tool, or production code restructured for the tool. Methods the tool
still cannot discover, such as `@property` methods, carry an explicit
limitation, and per-module reports never imply coverage of undiscovered code.
The v0.1.0 per-module floor, ten-mutant minimum, and differential scope rules
continue to apply.

### Quality-Adjusted Workflow Simulation

The simulator may later model software quality as a separate, optional layer
over the review workflow. The first step is a versioned quality-outcome
contract that defines an introduced defect, detection by tests or review,
post-merge escape, severity, detection delay, and remediation work. Historical
linkage must be explicit and conservative; a requested change, a failed check,
or a closed pull request is not itself a defect.

Quality evidence must retain separate tiers: pre-merge CI or test failure,
static-analysis finding, confirmed functional defect, production incident or
regression, revert, and remediation change. A static finding is a quality-risk
proxy, and a revert is an operational signal; neither is silently promoted to
an escaped-defect label. Benchmark test passage is also not production-quality
evidence. Every tier records its observation window, denominator, linkage basis,
and censoring or missingness treatment.

Defect incidence uses changed-code size as an exposure measure, not as a
standalone causal rule. Candidate predictors include added and deleted lines,
file or module churn, complexity or dependency fan-out where available,
historical defects, tests and CI evidence, ownership familiarity, review depth,
and task type. Sparse and overdispersed defect counts require uncertainty-aware
calibration and held-out descriptive validation. Source-code metrics are
optional future inputs and do not expand the v0.1.0 ingestion boundary.

AI-origin effects are modeled as declared, uncertain cohort assumptions or
interactions, never as a universal multiplier or an inferred percentage of
AI-written code. Human, AI, non-AI automation, and unknown origin remain
separate concepts, and unknown remains a valid result. Scenario comparisons
must show assumption sensitivity rather than present an AI effect as causal.

Agentic work records process dimensions separately from origin where evidence
exists: assisted versus agent-authored work, tool or agent family and version,
autonomy level, human intervention and revision effort, agent iterations, test
and tool-use behavior, reviewer engagement or abandonment, and repository
context or instructions. These observations must not be collapsed into a
single agent-quality score or treated as intrinsic contributor traits.

Merge behavior is modeled as a conditional merge or closure hazard based on PR
attributes such as task type, changed size and files, CI outcomes, review state,
review engagement, revisions, abandonment, policy, capacity, and queue
conditions, not as an intrinsic probability attached to an individual
contributor. If contributor or agent effects are eventually needed, they use
pseudonymous, pooled or hierarchical effects with shrinkage and minimum-sample
safeguards; default reports remain repository- and cohort-level and do not rank
people.

Validation must use temporal holdouts where possible, matched human baselines
where available, repository-level or hierarchical effects, and explicit
selection correction for merged-only or survivor-conditioned data. Agent,
repository, task, and language imbalance must be reported rather than hidden by
pooled rates. Observational associations must not be presented as intervention
effects.

An implemented quality layer may generate remediation work after escaped
defects, allowing defect detection and rework to consume review capacity and
alter later queue and merge outcomes. Reports may expose escaped-defect rates,
time to detection, remediation demand, and quality-adjusted throughput only
with their denominators, provenance, uncertainty, and censoring rules. The
feature must not claim productivity gains, safe approval policies, or
individual developer quality without intervention evidence; those claims remain
out of scope.

The first v0.2.0 quality slice is the data contract and descriptive reporting
of these signals, including optional CI and static-analysis observations. A
latent defect-introduction model, post-merge detection, remediation feedback,
and contributor or agent effects are subsequent milestones and require evidence
that passes the validation safeguards above. Source-code metrics remain
optional future inputs and do not silently expand the v0.1.0 ingestion boundary.

### End-to-End Holdout Validation Preparation

The real-data workflow can prepare a chronological training/validation split
from a collected dataset, calibrate only on the training interval, and emit the
versioned replay-evidence input consumed by `merge-carlo validate`. The holdout
replay uses only known-at-arrival attributes, requires adequate follow-up for
mature cohorts, and preserves dataset, model, and replay content hashes. A
held-out run remains distinguishable from an `in_sample_diagnostic`, even when a
declared descriptive gate fails. The workflow does not tune parameters on the
holdout or establish intervention validity.
