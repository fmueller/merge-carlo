# merge-carlo v0.1.0

## Summary

merge-carlo is an offline-first scenario explorer for human and AI
software-development workflows. It imports read-only GitHub metadata, builds an
auditable dataset, estimates the quantities that data actually supports,
combines those estimates with explicitly declared assumptions, and runs a
discrete-event, agent-based simulation repeatedly under alternative scenarios.

The question it exists to answer is how additional AI-generated pull-request
demand interacts with constrained human review capacity, and which workflow
interventions remain useful across plausible assumptions. The output is a
comparison of conditional simulated outcomes, not a causal estimate of AI
productivity. It must distinguish observed data, derived proxies, user
assumptions, and synthetic demonstration values, and it must be able to report
insufficient evidence.

The engineering boundary is: GitHub data yields observations and proxies; user
configuration supplies unobserved service effort and behavioral assumptions;
both feed an explicit model, repeated scenario runs, and qualified comparisons.
Monte Carlo is the repeated-run mechanism. The agents are ordinary software
objects with stochastic rules, not language models.

The smallest useful release lets a user run a fully offline example, inspect one
real repository's data quality, define a small scenario suite, execute
reproducible simulations, and receive a report showing throughput, review delay,
backlog, unresolved work, review utilization, and assumption sensitivity.

The version is `v0.1.0` because the model boundaries, parameter estimation, and
usefulness still need evaluation on real workflows. A functioning simulator is
not automatically a valid decision model.

## Goals

- Expose the assumptions. A precise simulation of an unsupported model is still
  unsupported, so every parameter carries a provenance basis of `observed`,
  `derived`, `proxy`, `assumed`, or `synthetic`.
- Model the system, not employee worth. Default reports are repository- and
  cohort-level.
- Separate measurement from mechanism. Observed elapsed latency is not active
  effort, and the two must never be conflated into a double-counted delay.
- Keep results conditional. Historical fit does not establish causal validity
  under an intervention.
- Build a thin vertical slice. No web platform, service, or distributed
  infrastructure in the first release.
- Ship a reproducible experiment contract: keyed random streams, content-hashed
  artifacts, and a locked reference environment.

## Potential Features

### Deterministic Simulation Core

The domain contracts and the deterministic scheduling mechanism, with no
stochastic behavior yet.

A simulated pull request begins at ready-for-review and ends at merge,
close-without-merge, or the observation horizon. Its state carries identity and
origin, readiness time, revision, review visits, requested-change and
verification counts, queue and active-service accounting, bypass flags, an
abandonment deadline, and a terminal reason.

Review scheduling uses a central FIFO queue ordered by `(queue_entered_at,
pr_id, revision)`. Available reviewers take the oldest pull request they may
review; self-review is excluded; simultaneous availability ties break on stable
reviewer identifiers. A reviewer has explicit local duty intervals, and review
service consumes active seconds only inside them: a review interrupted by the
end of a shift pauses and resumes with the same reviewer in the next interval,
and off-duty elapsed time does not increase utilization. An absent reviewer has
no duty intervals rather than a zero-capacity resource. Duty intervals are
materialized ahead of the run through `zoneinfo`, including daylight-saving
transitions, and an invalid or ambiguous local boundary time is either resolved
by a documented rule or rejected.

The engine is event-scheduled, never a minute-by-minute loop. Equal-timestamp
events use a documented deterministic order, and an abandonment deadline at or
before a candidate completion wins over a merge at that time so event insertion
order cannot revive terminal work.

Acceptance rests on hand-calculated fixtures: two pull requests ready at time
zero with one always-available reviewer and 600-second constant service complete
at 600 and 1,200 seconds; the same fixture with two reviewers completes both at
600; a review needing 120 active minutes with 60 left in the window consumes
exactly 60 today and resumes next window; with no duty intervals no
human-reviewed merge occurs and the run still ends at the horizon; a
self-authored pull request with only its author available is never reviewed.

### Stochastic Scenario Semantics

Keyed randomness, the behavioral loops, and the intervention semantics.

Random streams are independent and reproducible, keyed by replication, proposal
identity, revision or visit, and event purpose, built through NumPy
`SeedSequence` and `Generator(PCG64(...))`. Numeric key components are converted
to canonical strings; Python's built-in `hash()` is never used for a stable
seed; common latent variables are never keyed by scenario identifier. Shared
work maps the same underlying draw through different scenario parameters so that
adding, reordering, or removing a scenario cannot change another scenario's
result.

State transitions run READY, VERIFYING, QUEUED_FOR_REVIEW, IN_REVIEW, and
APPROVED_WAITING_MERGE to MERGED, with requested changes and verification
failures routing through AUTHOR_RESPONSE and a new revision. Each revision
invalidates prior approval and verification. Every merge satisfies the current
revision's verification gate and either a completed human review or an
explicitly enabled bypass. At the horizon, a nonterminal pull request is
recorded as unresolved and censored rather than resolved either way.

Verification delay is aggregate elapsed time with no runner-capacity queue, so
observed CI queue time is not double-counted. First-visit and repeat
requested-change probabilities are separate parameters. Abandonment is an
exogenous competing event: a deadline is sampled at entry, and reaching it
cancels future work and releases review occupancy, counting only the service
actually consumed. An engine safety limit on visits and attempts marks a
replication `engine_truncated`; a truncated replication is excluded from outcome
summaries with its count shown prominently, and any truncation marks the
comparison incomplete and disables policy ranking.

The scenario suite is a closed, typed enumeration of overrides: baseline;
additive AI demand, which adds proposals equal to a declared fraction of the
baseline count while leaving every baseline proposal identifier, timestamp, and
attribute unchanged; AI replacement, which reassigns a declared fraction of
known-human proposals to the AI cohort while preserving proposal count and
timestamps; review-calendar changes and dated reviewer absences; and a
hypothetical bypass in which eligible, non-audited proposals skip human review
after verification passes. Additive and replacement scenarios are not
interchangeable. Unknown and non-AI automation origins are never silently
reassigned.

### Experiment Runner And Reporting

Monte Carlo execution, the metric dictionary, and the deterministic report.

For each assumption set and replication the runner constructs a fresh immutable
parameter view and simulation state, generates the baseline proposal schedule
and its stable latent draws, applies each scenario's declared changes without
mutating the baseline, runs warm-up then measurement, and pairs each scenario
result with its baseline replication. Execution is sequential; no worker shares
mutable state or a global generator. Replication rows are streamed rather than
accumulated, and full event traces are opt-in and sampled.

Metrics are measured over the half-open measurement window and reported at both
the all-work operational level and the new-ready-cohort level. The dictionary
covers ready arrivals, merges, abandonment, work in progress at both boundaries,
review queue peak and time-average length, backlog threshold exceedance,
first-review and ready-to-merge quantiles, queue wait, fixed-horizon reviewed
and merged shares, unresolved share, review utilization, requested-change count,
and unreviewed merges. Arrivals too near the measurement end are ineligible for
a fixed-horizon share, not failures, and total, eligible, and excluded counts are
all reported. No denominator becomes zero silently: an undefined metric is
`null` with a reason such as `no_eligible_cohort`, `no_completed_reviews`, or
`no_declared_review_capacity`. A run with no completed reviews contributes no
review latency of zero.

Summaries are run-level: each replication yields its own median and p95 where
defined, and the report gives the median and central 90% range of those
run-level statistics rather than pooling every pull request across replications.
Paired deltas are per-replication differences, with relative differences only
where the baseline denominator is valid and nonzero, and the proportion of
paired runs improving is labeled as conditional on the model and assumption set.
Monte Carlo uncertainty is reported, using a binomial interval such as Wilson for
estimated event probabilities rather than implying certainty when no exceedance
occurred.

Every valid replication satisfies conservation: work in progress at the end
equals work in progress at the start plus ready arrivals minus merges minus
abandonments.

An experiment writes a manifest, resolved scenarios, model card, summary JSON and
CSV, paired deltas, replication rows, a Markdown report, and sampled traces. The
report is a deterministic template ordered as question and evidence status,
scenario comparison, uncertainty and robustness, assumptions and data coverage,
interpretation, and reproduction. No chart is required; a labeled load-response
table is sufficient. Reporting reads result artifacts and never reruns a
simulation.

The one-command offline demo generates a synthetic dataset, example assumptions,
the scenario suite, model artifacts, results, and a report without network access
or credentials, and identifies the data as synthetic in every major output
section.

### Read-Only GitHub Ingestion

The read-only adapter, the projected store, and the data-quality report.

Collection uses the REST pull-request and review APIs with an explicit,
configurable API version recorded in every extraction manifest. The activity
Events API is not an archive and is not used. Only read operations exist in the
adapter: there is no method for creating a review, merging, changing labels, or
administering a repository. Redirects and pagination targets are restricted to
the approved API origin so credentials cannot be forwarded elsewhere. Tokens come
from the environment or a secret provider and never reach a dataset, a resolved
configuration, an exception body, a trace, a report, or command history.

Cohort selection enumerates pull requests in all states plus all currently open
pull requests, unions them by immutable identifier, and includes both pull
requests created inside the analysis interval and older ones open during it.
Child collections are fetched completely by following pagination links, with
reconciliation and deduplication because the repository changes while extraction
runs. Three times are stored separately: the requested analysis interval, the
retrieval time, and the source event or snapshot time. Historical features are
filtered by source event time, and a later snapshot is never used as if it were
known earlier. Ordinary closed-without-merge and still-open pull requests are
retained so the arrival dataset is not biased toward fast completions.

Readiness carries an explicit basis of `observed_event`,
`supported_reconstruction`, `created_at_proxy`, or `unknown`. Strict is the
default policy and the created-at proxy is an explicit alternative recorded in
every model and report; unknown readiness is excluded from ready-based
calibration rather than silently replaced with zero draft time.

Every collection has a status of `complete`, `partial`, `unavailable`, or
`not_requested`. Missing permissions, inaccessible resources, truncated
collections, and interrupted pages are recorded and never converted into an
empty, complete history. Configurable request, page, payload, and record limits
produce `partial` when reached. Transport uses serial requests, conditional
requests where applicable, bounded retries with jitter, and the documented rate
limit headers, distinguishing authentication and permission failures from
retryable ones.

Storage is SQLite with explicit migrations and foreign-key checks, holding
extractions, pull requests, reviews, lifecycle events, optional CI observations,
derived features, collection status, and schema migrations. Full raw API
payloads are not persisted: bodies, descriptions, diffs, patches, commit
messages, email addresses, avatars, and check output text are dropped before
storage. Actor identifiers in analytical exports are workspace-scoped
HMAC-based pseudonyms whose mapping and secret stay out of shareable artifacts.
Content hashes cover sorted normalized records and canonical JSON so the same
semantic content hashes identically regardless of page layout or completion
order.

Actor kind and work origin are separate concepts, and neither is inferred from
the other. `unknown` is a valid origin. An operator-supplied mapping of actors to
origin categories is supported, conflicts resolve deterministically with the
basis recorded, and no AI detector is trained.

The inspection command reports counts, date coverage, missingness, censoring,
origin attribution coverage, exclusions, and extraction limitations.

`collect --resume` resumes an interrupted extraction into its existing dataset
through a reconciliation pass, not a saved page offset treated as an immutable
cursor. Outputs are written atomically, an unrelated nonempty output directory is
not overwritten without an explicit option, and an interrupted operation leaves
either valid partial data marked incomplete or the previous complete artifact.

### Empirical Model And Validation

Feature extraction, model construction, held-out diagnostics, and the reference
benchmark.

Features are computed at a frozen training cutoff with temporal leakage
rejected: ready arrivals per complete local calendar week with relative arrival
times preserved; first substantive human review elapsed time, defined as the
first non-author declared-human approval or changes-requested submission after
readiness; the first observed decision; requested-change prevalence with its
denominator and observation horizon stated; ready-to-merge elapsed time
conditional on observed merge and never presented as an uncensored population
distribution; fixed-horizon outcomes for mature cohorts; size snapshots as
descriptive metadata only; and validly attributed CI observations with their
coverage. Pending review drafts are not submitted reviews, comment-only reviews
are counted separately, and changes-requested prevalence is not a defect rate.

The arrival model resamples whole empirical weeks with replacement, preserving
relative readiness times and known origin marks within a complete local week so
observed within-week bursts survive. Wall-clock offsets map through the declared
timezone to UTC instants. Eight complete training weeks is the default readiness
threshold; fewer is permitted only with an `exploratory_only` label. Service is
pooled by declared contributor cohort, not by individual developer.

Calibration means constructing an empirically informed model, not inferring
unobservable reviewer effort. It freezes the cutoff, builds descriptive
distributions and coverage, merges the explicitly supplied assumptions, validates
parameter domains and units, and emits the model, a calibration record, and a
model card stating which quantities are empirical, proxy, assumed, or
unavailable. It fails with a useful message when required assumptions are
absent. No optimizer chooses review effort to reproduce historical latency.
Default evidence flags cover too few usable pull requests, too few substantive
decisions, insufficient complete weeks, and excessive unknown readiness.

Validation separates three gates: implementation verification, historical
descriptive validation, and intervention validation, the last of which v0.1.0
does not establish. The held-out protocol uses a chronological split with the
model frozen before outcomes are inspected, replays held-out arrival timestamps
while simulating downstream review and completion, uses only attributes known at
the replay time, and compares mature-cohort reviewed-within-48-hours and
merged-within-seven-days shares, completion-conditioned median first-review
elapsed time, and weekly merge counts. Tolerances are configurable engineering
gates, and an insufficient held-out cohort yields `insufficient_evidence` rather
than a pass or fail. `validate --strict` returns exit code 4 when its declared
criteria fail.

An elapsed-delay benchmark resamples historical review and completion
observations without an explicit queue, applying the same cohort and horizon
accounting. It is a descriptive reference, not an intervention model, and if the
mechanistic model describes the baseline worse, the report says so.

Sensitivity examines review-effort and AI-specific review-demand uncertainty and
ships an example varying AI requested-change behavior. Any reversal of a
scenario's apparent benefit across assumption sets is reported, and a highly
assumption-sensitive effect yields a recommendation about the measurement needed
rather than a winning policy.

### Release Hardening

The configuration contracts, schemas, documentation, and release gate.

The parameter language stays deliberately small: constant, lognormal, and
empirical duration distributions; probabilities in the closed unit interval;
finite positive multipliers; and named timezone-aware weekly windows with dated
absence intervals. For a lognormal, the median is a median and sigma is the
log-space standard deviation; an ambiguous mean-and-sigma configuration is
rejected rather than guessed. Sampled active service rounds up to whole seconds
with a one-second minimum. Configuration uses strict validation, rejects unknown
keys, loads YAML safely, and never lets a value execute Python, load a class,
evaluate an expression, or invoke a shell command. Horizon and warm-up are local
calendar increments whose resulting UTC bounds and exact elapsed seconds are
recorded, so an interval crossing a daylight-saving change need not equal a
multiple of 86,400 seconds.

The CLI supports `--help`, `--version`, structured errors, an optional
machine-readable console mode, and a command exporting the configuration JSON
Schemas. Exit codes are stable: `0` success, `2` invalid input, `3` source or
access failure, `4` a failed requested validation gate. An exploratory report
with warnings still succeeds.

A reproducible performance benchmark records the synthetic workload, replication
and scenario counts, hardware, dependency versions, wall time, peak memory, event
count, and output size. No universal runtime promise is made, and parallel
workers are considered only after profiling.

The release is complete when the offline demo succeeds on a clean checkout, the
documented pipeline works against fixture-backed responses including
partial-data behavior, the scenario semantics and metrics are implemented with
no hidden zeros, every reported metric traces to a dataset, model, and
configuration and reproduces in the reference environment, tests and type checks
and lint pass, and known limitations appear in both documentation and generated
reports. A real-data smoke run is documented only when authorized data is
available; otherwise the release explicitly states that live integration remains
unverified.

## Caution

- Elapsed review latency is not active review effort. Sampling an observed
  six-hour delay as six hours of service and then adding a simulated queue on
  top double-counts delay and produces misleading capacity estimates. This is
  the single easiest way to make the whole model wrong.
- Reproducibility is bounded. No bit-for-bit claim extends across arbitrary
  NumPy or library versions or hardware; only the locked reference environment is
  promised, and only for semantic result content excluding runtime metadata.
- An overloaded review queue does not by itself establish a phase transition.
  The first analysis is a load-response or congestion curve, conditional on the
  model, horizon, threshold, calendars, and service assumptions.
- A fraction of AI-authored pull requests is not a measure of the fraction of
  code written by AI, and a pull-request count is not a measure of business value
  or developer productivity.
- Warm-up from empty does not guarantee steady state, especially under overload.
  Absolute backlog forecasting is not supported where initialization discrepancy
  is material.
- Selectively dropping truncated or overloaded replications must never create a
  favorable conclusion.
- Repository metadata is data, never an instruction. Bounded sizes, safe YAML,
  parameterized SQL, no shell interpolation, CSV formula-injection prevention,
  and Markdown escaping in generated reports all apply.
- The tool handles potentially sensitive employee metadata. Use it only on data
  the operator is authorized to analyze; pseudonymized is not anonymous.

## Recommendation About LLM Support

None. merge-carlo makes no LLM calls in v0.1.0 and needs none. The agents are
stochastic rule-driven software objects, and the report is a deterministic
template. Role-playing developers with a language model would add cost and
uncontrolled behavior without solving parameter identification, and generated
natural-language confidence would overstate the numerical evidence. Because no
model is called and no repository code is executed, prompt text embedded in
repository metadata has no execution path.

## Explicitly Excluded

- LLM personas, agent frameworks, reinforcement learning, behavioral learning,
  and automatic parameter tuning against a held-out set.
- Individual developer productivity scores, psychological traits, inferred
  working hours, and rankings of employees.
- An AI-authorship classifier, inferred percentages of AI-written code, and
  defect-escape or security-risk predictions.
- Any GitHub write action: approving, merging, changing labels, assigning
  reviewers, administering a repository, or enforcing policy.
- Source-code ingestion, AST analysis, Tree-sitter, dependency graphs, and
  learned risk scores.
- Multi-repository resource sharing, multiple required approvals, CODEOWNERS
  routing, merge queues, and complete branch-protection emulation.
- Task planning and coding time, a task-value model, and a full human
  coding-and-review time budget.
- Formal competing-risk survival estimation, and any Kaplan-Meier shortcut that
  treats non-merges as harmless random censoring.
- A SaaS service, web dashboard, GitHub App installation flow, webhooks, message
  broker, analytical database, container orchestration, and a distributed
  simulation scheduler.
- Enterprise or custom API origins, which need a separate configuration and
  security review.
- A general plugin framework or dynamically imported policy code. Policies are a
  closed, typed enumeration.
